存储引擎
    mysql体系结构
        连接层 --- 连接池---与客户端连接，校验用户名和密码即授权验证，校验每一个客户端所具有的权限
        服务层 --- SQL接口 解析器 查询优化器 缓存 --- 绝大部分核心功能，以及所有跨存储引擎的实现
        引擎层 --- 提供很多可插拔存储引擎（可拓展） --- 存储引擎控制数据库中数据的存储和提取方式，注意index在引擎层实现，所以不同的引擎索引不同
                    InnoDB引擎是mysql5.5版本后默认的存储引擎
        存储层 --- 存数据，包含各种日志，数据
    存储引擎简介
        就是各种数据库技术的实现方式，存储引擎是基于表的，而不是基于库的，所以存储引擎也可以被称为表类型，所以一个数据库下的多张表可以是不同引擎的
        如何指定引擎：
            create table 表名(
                //
            )engine = 引擎名;
        查看当前数据库所支持的引擎


    存储引擎特点
        InnoDB --- 兼顾高可靠性和高性能的通用存储引擎
               --- DML操作遵循ACID模型 支持事务
               --- 行级锁 提高并发访问性能
               --- 支持外键约束，保证数据完整，正确
               --- 文件：xxx.ibd xxx代表表名 每张表对应一个表空间文件，存储该表的表结构（frm、sdi）、数据和索引
                        参数 innodb_file_per_table 决定是表共用一个表空间文件，还是一张表对应一个，mysql8.0中为开启，即一对一
               --- 逻辑存储结构
                    tablespace 表空间
                    segment 段
                    extent 区
                    page 页
                    row 行
                    表空间中有多个段，中有多个区，中有多个页，中有多个行，行就是表中一行行的数据，行中存储Trx id --最后一次操作事务的id
                roll pointer -- 一些指针 n个column 区的大小固定为1M 一个页大小固定为16K
        MyISAM --- mysql早期默认的存储引擎
               --- 不支持事务，外键行锁，支持表锁
               --- 访问速度快
               --- 文件：.MYD--存放数据 .MYI--存储索引 .sdi--存放表结构
        Memory --- 表数据存储在内存中，由于硬件问题或断电问题的影响，只能将这些表作为临时表或缓存使用
               --- 由于内存存放，访问速度快 默认使用hash索引
               --- 文件：.sdi--存储表结构信息
    存储引擎选择
        InnoDB --- 应用对事物的完整性有较高要求，在并发条件下要求数据的一致性，数据操作除了插入和查询，还包含很多更新 删除，那么选InnoDB
        MyISAM --- 如果应用以读和插入为主，只有很少的更新和删除操作，且对事务的完整性，并发性要求不高，那么MyISAM是非常合适的
        Memory --- 临时表和缓存 缺陷是表的大小有限制，且数据不安全

索引
    索引概述
        介绍
            索引（index）是帮助mysql高效获取数据的数据结构（有序），数据之外，数据库维护着满足特定查找算法的数据结构，这些数据结构以某种方式引用数据，这样
        就可以在这些数据结构上实现高级查找算法

        优缺点
            优：1 提高数据检索效率，降低IO成本 2 通过索引列对数据进行排序，降低数据排序的成本，降低CPU消耗
            劣：1 占用空间 2 降低更新表的速度
    索引结构 --- 在存储引擎层实现，不同的存储引擎有不同的结构
        二叉树 极端情况链化 -- 改进为红黑树 数据过多层级过高 -- 改进为B树
        B+Tree索引 --- 最常见，大部分引擎支持 （InnoDB、MyISAM、Memory）
        Hash索引 --- 底层由哈希表实现，只支持精确查询，无法利用索引完成排序，查询效率高，通常只需要一次检索 （仅Memory，但InnoDB中有自适应hash功能）
        R-tree空间索引 --- 是MyISAM引擎的一个特殊索引类型，主要用于地理空间数据类型，通常使用较少 （仅MyISAM）
        Full-text全文索引 --- 是一种通过建立倒排索引，快速匹配文档的方式 （5.6后的InnoDB和MyISAM）

        B树的构建 --- n阶B树每个结点有n-1个值（key），有n个指针，插入值时与原有值进行比较，小在左大在右，插入后如果结点内值个数超过n-1，则取中间数向上分裂，变为父结点
            剩余key遵循小于父在左，大于父在右
        B+Tree --- 与B树不同在所有元素都会出现在叶子结点，非叶子结点仅提供索引。所有叶子结点形成了一个单向链表。分裂时上移后小于父在左，小于等于父在右
        mysql索引数据结构对经典B+Tree进行优化，增加指向相邻叶子结点的链表指针，就形成了带有顺序指针的B+Tree，提高区间访问的性能

        为什么使用B+Tree而不是B树？---因为B树和B+Tree的每个结点都存储在一个页中，而B+Tree非叶子结点不存储数据，那么这一页就有更多的空间去存储指针和key，那么数据量相
            同的情况下，B+Tree的层级会更少。此外，B+Tree无论查找哪个数据，都需要到叶子结点中查找，效率稳定。而且，在B+Tree中，叶子结点形成了一个双向链表，便于范围搜
            索和排序
        注：由于B+Tree是B树的变种，所以在Linux中也会展示为BTree

    索引分类
        主键索引---针对表中主键创建的索引---默认自动创建且唯一---primary
        唯一索引---避免表中数据列的值重复，加唯一约束的时候就会自动创建---可以多个---unique
        常规索引---快速定位特定数据---可以多个---无
        全文索引---查找文本中关键字，而不是比较索引的值---可以多个---fulltext

        在InnoDB引擎中，根据索引的存储形式，又能分为
        聚集索引---将数据存储与索引放到一块，索引结构的叶子结点保存了行数据---必须有，且唯一
        二级索引---将数据和索引分开存储，索引结构的叶子结点关联的是主键---可以存在多个

        聚集索引选取规则：
            如果存在主键，主键索引就是聚集索引
            如果不存在主键，会使用第一个唯一索引作为聚集索引
            如果既没有主键，也没有唯一索引，则InnoDB会自动生成一个rowid作为隐藏的聚集索引
        查询时，如果查询的是二级索引的内容，会先找到目标对应的主键值，然后在拿着这个主键值回到聚集索引中来找数据，称为回表查询
    索引语法
        创建索引
            create [unique|fulltext] index index_name on table_name (index_col_name,...);
        查看索引
            show index from table_name
        删除索引
            drop index index_name on table_name
    SQL性能分析
        SQL执行频率 --- 数据库是否需要优化与进行哪种操作的频率更高相关
            mysql客户端连接成功后，通过show [session | global] status命令可以提供服务器状态信息，通过如下指令查询各操作访问频次
                show global status like 'Com_______'（七个下划线）
            查询出操作执行频次后，如果select语句的频次较高，则需要进行优化，那么哪些语句需要优化呢，就需要根据慢查询日志来定位sql语句

            慢查询日志记录了所有执行时间超过指定参数（long_query_time，单位 秒 默认10s）的所有sql语句的日志
                show variables like 'slow_query_log'可以查看慢查询日志是否开启
            mysql的慢查询日志默认不开启，需要在mysql的配置文件(/etc/my.cnf)中配置如下信息
                slow_query_log=1 --开启慢查询日志
                long_query_time=2 --设置慢日志的时间为2s，超过视为慢查询
            配置完毕后，通过指令重启mysql服务器 并进行测试，查看慢查询日志文件中的信息 文件位置在Linux中一般为 /var/lib/mysql/localhost-slow.log

            当慢查询日志解决不了我们的问题，比如一个简单的查询很接近慢日志时间，也需要优化，但这时候并不会显示在慢日志当中，我们就可以用profile详情
            show profiles;可以帮助我们了解时间都耗费到哪里去了，通过select @@having_profiling可以看到当前mysql是否支持profile操作
            确认支持后还需要开启，默认profiling是关闭的，可以通过set在session或global级别开启profiling
                show profiles; --查看每一条SQL的耗时基本情况
                show profile for query query_id; --查看指定id的SQL语句各个阶段的耗时情况
                show profile cpu for query query_id --查看指定id的SQL语句的CPU使用情况

            以上都是粗略的查看执行时间，想要真正的看一条SQL语句的性能，还要通过explain执行计划
            explain或desc命令获取mysql如何执行select语句的信息，包括在select语句执行过程中表如何连接和连接的顺序
                --直接在任意select语句前加explain/desc
                explain select 字段列表 from 表名 where 条件;
            explain查询出的内容有很多列，每个列的含义如下
                id --- select查询的字段号，表示查询中执行select子句或操作表的顺序，id相同，执行顺序从上到下，id不同，值越大越先执行
                select_type --- 表示select的类型，常见的取值有simple（简单表，即不用表连接或子查询）、primary（主查询，即最外层）、
                            union（union中的第二个或后面的查询语句）、subquery（select/where之后包含了子查询）等
                type --- 重点关注，表示连接类型，性能由好到差的连接类型为null（不访问任何表）、system（访问一张系统表）、const（根据主键和唯一索引访问）、
                    eq_ref、ref（使用非唯一性的索引进行查询）、range、index（用了索引但是遍历整个索引树）、all（全表扫描），优化时尽量往前优化
                possible_key --- 这张表上可能用到的索引
                key --- 实际用到的索引
                key_lens --- 索引中使用的字节数，该值为索引字段最大可能长度，并非实际，不失精确的前提下越短越好
                rows --- mysql认为必须要执行查询的行数，在InnoDB引擎的表中，是一个估计值，可能不总是准确的
                filtered --- 表示返回结果的行数占需读取行数的百分比，越高越好
    索引使用
        使用规则
            最左前缀法则
                联合索引（索引了多列）遵循，指查询从索引的最左列开始，并且不跳过索引中的列，如果跳跃，索引将部分失效（后面字段的索引失效）
                注意：最左前缀法则仅仅要求最左列存在，跟最左列的位置无关
            范围查询
                联合索引中 出现范围查询（>,<） 范围查询右侧的列索引失效，尽量用<= >=
            索引列运算
                不要在索引列上进行任意运算操作，包括函数，否则索引会失效
            字符串不加引号
                如果字符串类型字段使用不加引号，索引将失效
            模糊查询
                如果仅仅是尾部模糊匹配，索引不会失效，如果是头部模糊匹配，索引失效
            or连接的条件
                用or分割开的条件，如果or前的条件中有索引，而后面的列中没有索引，那么涉及的索引都不会被用到
                or的两边要各自有自己的索引才可以用索引
            数据分布影响
                如果mysql评估使用索引比全表扫描慢，就不会使用索引
            SQL提示---当一个字段，既有联合索引，且该字段是最左字段，又有单独索引，那么mysql内部优化器会自动为你选择该使用哪个索引，当我们想要自己决定，就需要SQL提示
                --use index 要使用哪个索引，只是一个建议，至于mysql用不用，还得自己权衡一下
                explain select * from tb_user use index(索引名) where ...
                --ignore index 不使用哪个索引
                explain select * from tb_user ignore index(索引名) where ...
                --force index 必须走这个索引
                explain select * from tb_user force index(索引名) where ...
            覆盖索引
                尽量使用（查询使用的索引，并且需要返回的列，在该索引中已经能够全部找到），减少select *
                就是尽量写清要查的字段，而不是简单的写*，减少回表查询，执行计划的区别在于extra字段
                using index condition ---查找使用了索引，但需要回表查询
                using where; using index --- 查找使用了索引，但所需数据在索引列都能找到，所以不需要回表查询
            前缀索引---当字段类型为字符串，有时需要索引很长的字符串，这会让索引变得很大，查询时，浪费大量的磁盘IO，影响查询效率，此时可以只将字符串的一部分前缀，建立索引
                    节约空间，提升效率
                语法 --- create index idx_xxx on table_name(column(n)); n代表提取前几个字符构建索引
                前缀长度可以根据索引的选择性来决定，而选择性是指不重复的索引值（基数）和数据表的记录总数的比值，索引选择性越高则查询效率越高
                选择性可以根据两个公式来求取
                    select count(distinct str) / count(*) from table_name;
                    select count(distinct substring(str, num1, num2)) / count(*) from table_name --num1和num2决定取用str中的前多少个字符作为前缀
                利用前缀获取数据后，往往会再对比一次，确保取出的数据无误
            单列索引和联合索引
                业务场景中，如果存在多个查询条件，考虑针对查询字段建立索引时，建议建立联合索引，而非单列索引
                
    索引设计原则
        1 数据量大 查询频繁的表，需建立索引
        2 针对常作为where、order by、group by操作的字段建立索引
        3 尽量选择区分度高的列，尽量建立唯一索引
        4 如果字符串，长度过程，应用前缀索引
        5 尽量使用联合索引 尽量使用覆盖索引
        6 要控制索引的数量，索引越多，维护索引的开销越大，影响增删改
        7 如果索引列不能存储null 请在创建表的时候用not null来约束，当优化器知道每列是否包含null 它可以更好的确定哪个索引最有效的用于查询
